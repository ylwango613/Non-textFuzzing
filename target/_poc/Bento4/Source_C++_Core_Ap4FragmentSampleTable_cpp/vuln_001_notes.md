# VULN 001 — PoC Notes

## Vulnerability
**Title**: Integer overflow in `AP4_Array::EnsureCapacity` → heap buffer overflow in `AP4_FragmentSampleTable::AddTrun`

**Source**: `Source/C++/Core/Ap4FragmentSampleTable.cpp` and `Ap4Array.h`

## Root Cause

In `AP4_Array<T>::EnsureCapacity(AP4_Cardinal count)`:

```cpp
T* new_items = new T[count];  // 'count' passed from AddTrun
```

When called from `AP4_FragmentSampleTable::AddTrun` with a trun atom whose
`sample_count=0x20000000` and no per-sample flags (flags=0x000001, data_offset only),
the code attempts to resize the internal array to 0x20000000 elements.

- **32-bit build**: `0x20000000 * sizeof(AP4_Sample)` wraps to 0 (integer overflow in the
  allocator's size calculation), so `new T[count]` allocates 0 bytes but sets
  `m_AllocatedCount = 0x20000000`. The subsequent construction loop then writes ~536M
  `AP4_Sample` objects to unallocated memory → heap buffer overflow.

- **64-bit ASAN build**: The full allocation size does not overflow 64-bit arithmetic,
  so `new T[count]` requests ~21 GB of memory, which fails with `std::bad_alloc` (uncaught
  exception) → abort / crash (DoS).

## Trigger

A crafted fragmented MP4 containing:
- `moof → traf → trun` with `version=0`, `flags=0x000001` (data_offset only),
  `sample_count=0x20000000`, and no per-sample fields.

## Expected Behavior

| Build        | Expected outcome                                          |
|--------------|-----------------------------------------------------------|
| 32-bit       | ASAN heap-buffer-overflow in `AP4_FragmentSampleTable::AddTrun` |
| 64-bit ASAN  | `std::bad_alloc` (uncaught) → abort / SIGABRT             |
| 64-bit no-ASAN | Process killed by OOM or `std::terminate` crash         |
