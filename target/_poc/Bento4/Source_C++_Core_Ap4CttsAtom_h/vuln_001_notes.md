# VULN-001: Integer Overflow in AP4_CttsAtom Constructor

## Vulnerability Summary

**CWE**: CWE-190 (Integer Overflow) → CWE-122/125 (Heap Buffer Over-Read/Write)
**File**: `Bento4/Source/C++/Core/Ap4CttsAtom.h` / `Ap4CttsAtom.cpp`

## Root Cause

In the `AP4_CttsAtom` constructor (lines 78-97 of Ap4CttsAtom.cpp):

1. `entry_count` is read directly from the MP4 stream as `AP4_UI32` (32-bit unsigned integer)
2. A buffer is allocated: `new unsigned char[entry_count * 8]`
   - When `entry_count >= 0x20000000`, the multiplication overflows a 32-bit integer
   - Example: `0x20000001 * 8 = 0x100000008`, which truncates to `8` (mod 2^32)
   - Only **8 bytes** are allocated instead of the expected ~4 GB
3. The loop then runs `entry_count` (536,870,913) iterations, accessing `buffer[i*8]`
   - At `i=1`, it already reads 8 bytes beyond the 8-byte allocation → **heap OOB read**
   - This constitutes a heap buffer over-read (and potentially over-write) condition

## PoC Approach

The crafted `vuln_001.mp4` contains:
- A complete, minimal MP4 structure so mp42aac can parse far enough to reach the ctts atom
- A `ctts` box with:
  - Box size field = 24 bytes (actual data in file: header + 1 real entry)
  - `entry_count` field = `0x20000001` (536,870,913)
  - Only 1 actual entry (8 bytes) present in the file

When the Bento4 parser reads this box:
1. It reads `entry_count = 0x20000001`
2. Allocates `0x20000001 * 8 = 8` bytes (integer overflow → tiny allocation)
3. Reads 8 bytes into the buffer (the single entry present in the file)
4. Begins looping 536,870,913 times, accessing `buffer[i*8]` → immediate OOB at i=1
