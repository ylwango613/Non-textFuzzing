# VULN 001: Integer Underflow in AP4_IproAtom → Out-of-Bounds Read

## Summary

- **File**: `Bento4/Source/C++/Core/Ap4IproAtom.cpp`
- **Function**: `AP4_IproAtom::AP4_IproAtom()` (constructor)
- **Line**: 70
- **CWE**: CWE-191 (Integer Underflow) → CWE-125 (Out-of-Bounds Read)
- **Binary**: `mp42aac` (ASAN+UBSAN build)

## Root Cause

`AP4_IproAtom::Create()` (line 49) performs the guard:
```cpp
if (size < AP4_FULL_ATOM_HEADER_SIZE) return NULL;
// AP4_FULL_ATOM_HEADER_SIZE = 12
```

With `size=12`, the check `12 < 12` evaluates to **false**, so parsing continues.

The constructor then computes (line 70):
```cpp
AP4_LargeSize bytes_available = size - AP4_FULL_ATOM_HEADER_SIZE - 2;
//                             = 12 - 12 - 2
//                             = 0xFFFFFFFE  (AP4_UI32 unsigned underflow)
```

This unsigned wrap-around produces `0xFFFFFFFE` ≈ 4 GB.  When zero-extended to
`AP4_LargeSize` (uint64_t) the value remains `0xFFFFFFFE`.

## Consequences

1. **`ReadUI16(entry_count)` at line 67** reads **2 bytes past the ipro atom's
   declared end**.  These bytes come from the outer container's data and are
   entirely attacker-controlled.

2. **`bytes_available = 0xFFFFFFFE`** disables the boundary guards inside
   `AP4_AtomFactory::CreateAtomFromStream()`:
   - Line 168: `if (bytes_available < 8)` — always false (4 GB >> 8)
   - Line 215: `if (size > bytes_available)` — passes for any sub-atom size
     up to ~4 GB

3. The loop at lines 71-79 calls `CreateAtomFromStream(stream, 0xFFFFFFFE, atom)`
   `entry_count` times, reading sub-atoms from **outside the ipro atom's
   declared boundary**.  All bytes read belong to the enclosing container or
   subsequent file data — a logical out-of-bounds read.

## Trigger Path

```
mp42aac main()
  → AP4_File::AP4_File(input_stream)
    → AP4_AtomFactory::CreateAtomFromStream(stream, bytes_avail, atom)
      → moov container parsed
        → udta container parsed
          → ipro atom found (size=12)
            → AP4_IproAtom::Create(size=12, stream, factory)
              → 12 < 12? No → continue
              → ReadFullHeader() consumes bytes [8-11] of ipro
              → AP4_IproAtom::AP4_IproAtom(12, 0, 0, stream, factory)
                → ReadUI16(entry_count)  ← reads 2 bytes PAST ipro end (OOB #1)
                → bytes_available = 12-12-2 = 0xFFFFFFFE (UNDERFLOW)
                → for i in range(entry_count):
                    CreateAtomFromStream(stream, 0xFFFFFFFE, atom)  (OOB #2)
```

## Crafted MP4 Structure

| Atom  | Offset | Size | Notes |
|-------|--------|------|-------|
| ftyp  | 0      | 20   | major brand "mp42" |
| moov  | 20     | …    | container |
|  mvhd | 28     | 108  | standard movie header (version 0) |
|  udta | 136    | 30   | container |
|   ipro| 144    | 12   | **size=12** — triggers underflow |
|   [entry_count] | 156 | 2 | `0x00 0x01` = 1, read OUTSIDE ipro |
|   [fake free]   | 158 | 8 | `size=8, type='free'` — parsed OOB |
| mdat  | …      | 8    | empty media data |

After `AP4_IproAtom::Create()` returns, the outer `CreateAtomFromStream` seeks
the stream back to `ipro_start + 12 = 156`.  The enclosing `udta` then tries
to parse the next child from that offset, reading `0x0001_0000 = 65536` as the
atom size (the `entry_count` + sub-atom bytes), which fails the bounds check
(`65536 > udta_remaining`) and terminates udta parsing gracefully.

## Expected Behaviour Under ASAN+UBSAN

- **Logical OOB read**: The `ReadUI16` and subsequent `CreateAtomFromStream`
  calls access bytes that fall outside the ipro atom's declared 12-byte
  boundary.
- **If the stream uses a heap-backed buffer** with ASAN red zones, the 2-byte
  read past ipro's end may produce a **heap-buffer-overflow** report.
- **Without a direct heap OOB**: the program may run without crashing but with
  logically corrupted parsing state (UNVERIFIED).
