# VULN 002 — AP4_CttsAtom Missing entry_count Bounds Check → Uncontrolled Memory Allocation (DoS)

## Summary

A missing bounds check in the `ctts` (Composition Time to Sample) atom parser in Bento4 allows a crafted MP4 file to trigger massive uncontrolled memory allocations, leading to an Out-of-Memory condition or process crash (DoS).

## Affected Component

- **File**: `Source/C++/Core/Ap4CttsAtom.cpp`
- **Lines**: 78–82
- **Binary**: `mp42aac` (and any other Bento4 tool that parses MP4 files)

## Vulnerable Code

```cpp
AP4_UI32 entry_count;
stream.ReadUI32(entry_count);             // line 78: no size check
m_Entries.SetItemCount(entry_count);      // line 79: UNBOUNDED vector allocation
unsigned char* buffer = new unsigned char[entry_count*8]; // line 80: UNBOUNDED heap allocation
AP4_Result result = stream.Read(buffer, entry_count*8);
```

## Root Cause

The `AP4_CttsAtom` constructor reads `entry_count` directly from the stream without validating it against the declared atom size. The constructor is called from `AP4_CttsAtom::Create()` only after checking `size >= AP4_FULL_ATOM_HEADER_SIZE` (12 bytes), but there is **no check** of the form:

```cpp
// Missing check (present in other atoms like stco, stsc, stsz):
if (entry_count > (size - AP4_FULL_ATOM_HEADER_SIZE - 4) / 8) return;
```

This contrasts with sibling atoms (`stco`, `stsz`, `stsc`) which all guard their entry counts against the declared atom size.

## Trigger Path

```
mp42aac main()
  → new AP4_File(*input)
    → AP4_AtomFactory::CreateAtomFromStream()
      → AP4_CttsAtom::Create(size=16, stream)
        → new AP4_CttsAtom(size=16, version=0, flags=0, stream)
          → stream.ReadUI32(entry_count)        // reads 0x04000000
          → m_Entries.SetItemCount(0x04000000)  // allocates ~256MB vector
          → new unsigned char[0x04000000 * 8]  // allocates ~512MB buffer
          → OOM / std::bad_alloc / process crash
```

## PoC Construction

The crafted MP4 contains a minimal but structurally valid hierarchy:

```
ftyp
moov
  mvhd
  trak
    tkhd
    mdia
      mdhd
      hdlr
      minf
        smhd
        dinf (dref + url)
        stbl
          stsd
          stts
          stsc
          stsz
          stco
          ctts  ← MALICIOUS BOX
```

The malicious `ctts` box has:
- Declared size = **16** bytes (8-byte header + 4 version/flags + 4 entry_count field only)
- `entry_count` = **0x04000000** (67,108,864)

This creates a discrepancy: the atom declares only 16 bytes total (with 0 bytes of actual entry data), but the code attempts to allocate memory for 67 million entries (approximately 780 MB total).

## Impact

| Allocation | Size |
|---|---|
| `new unsigned char[entry_count * 8]` | ~512 MB |
| `m_Entries.SetItemCount(entry_count)` (vector) | ~256 MB |
| **Total attempted** | **~768 MB** |

On systems without sufficient memory, this causes:
1. `std::bad_alloc` exception → unhandled → process abort
2. OOM killer termination
3. ASAN allocation failure (with ASAN builds)

Even on systems with sufficient memory, `stream.Read(buffer, entry_count*8)` will fail because the stream only has a few bytes remaining — the code then deallocates the buffer and returns, but the `m_Entries` vector (SetItemCount) allocation has already succeeded, wasting significant memory and potentially slowing the system.

## Comparison with Fixed Sibling Atoms

`stco` (Ap4StcoAtom.cpp) has a proper guard:
```cpp
AP4_UI32 max_entries = (size - AP4_FULL_ATOM_HEADER_SIZE - 4) / 4;
if (entry_count > max_entries) entry_count = max_entries;
```

`ctts` has no equivalent check.

## Fix Recommendation

Add a size-based bounds check before the allocations:

```cpp
AP4_UI32 entry_count;
stream.ReadUI32(entry_count);
// Validate: each entry is 8 bytes; available data = size - header(12) - entry_count_field(4)
AP4_UI32 max_entries = (size >= AP4_FULL_ATOM_HEADER_SIZE + 4)
                       ? (size - AP4_FULL_ATOM_HEADER_SIZE - 4) / 8
                       : 0;
if (entry_count > max_entries) return;  // or: entry_count = max_entries;
```
