# VULN 001 – FIC Heap OOB Write in fic_decode_slice — Analysis Notes

## Vulnerability Summary

- **File**: `libavcodec/fic.c`
- **Function**: `fic_decode_frame` / `fic_decode_slice`
- **Line**: 389 (`FFALIGN(avctx->height - ctx->slice_h * (nslices - 1), 16)`)
- **CWE**: CWE-787 (Out-of-bounds Write)
- **Claimed impact**: Heap OOB write when last-slice height rounds up past the frame buffer boundary

## Root Cause (Code Level)

In `fic_decode_frame`, the last-slice height is computed as:

```c
slice_h = FFALIGN(avctx->height - ctx->slice_h * (nslices - 1), 16);
```

`FFALIGN(x, 16)` rounds x UP to the next multiple of 16. When `avctx->height` is not a multiple of 16, this rounds the last slice height beyond the actual frame pixel rows. `fic_decode_slice` then iterates for `slice_h` rows (in 8-row IDCT-block steps), causing `fic_idct_put` to write 8 bytes per pixel column into rows that are beyond the logically allocated frame height.

## PoC Construction

- Container: AVI 1.0 (RIFF/LIST/AVIH/STRH/STRF/MOVI/IDX1)
- Codec FOURCC: `FICV`
- Dimensions: WIDTH=320, HEIGHT=100 (not a multiple of 16)
- nslices=1 (single slice, maximum rounding effect)
- FIC packet: 27-byte header + 4-byte slice offset table + 840 zero bytes of bitstream
  - 840 bytes = 840 blocks × 8 bits = all blocks for FFALIGN(100,16)=112 rows decoded
  - Each zero-byte block = [0: not skip][0000000: num_coeff=0] → `fic_idct_put` called, writes 8×8 zeros

## Why ASAN Does Not Detect the Overflow

### Calculated write range (Y plane)

| Parameter | Value |
|---|---|
| linesize[0] (FFALIGN(320, 64)) | 384 bytes |
| decoder writes (FFALIGN(100,16) = 112 rows) | 43,008 bytes |

### Actual pool buffer allocation

`update_frame_pool` in `libavcodec/get_buffer.c` calls `avcodec_align_dimensions2`, which for `AV_PIX_FMT_YUV420P` sets:

```c
w_align = 16;
h_align = 16 * 2;  // = 32  (interlaced needs 2 macroblocks height)
```

So `h = FFALIGN(100, 32) = 128` rows (not 100, not 112).

Pool Y buffer = `linesize[0] * h + 16 + STRIDE_ALIGN - 1`
             = `384 * 128 + 16 + 63`
             = `49,152 + 79`
             = **49,231 bytes**

### Result

The decoder writes 43,008 bytes. The pool Y buffer is 49,231 bytes.
43,008 < 49,231: **no bytes are written past the allocation boundary**.

ASAN correctly does not report an error.

### Exhaustive verification

A brute-force search over all heights 1–200 and nslices 1–8 confirms that
`total_rows_written > pool_rows` is never true when using FFmpeg's default
`avcodec_default_get_buffer2` allocator. The 32-row height alignment applied
to the pool always absorbs the 16-row rounding in the decoder.

### ASAN instrumentation IS present

Assembly inspection confirms that `fic_idct_put` in the ASAN-instrumented binary:
- Contains `__asan_report_load2` for each `int16_t` load from `block[]` (IDCT scratch)
- Contains `__asan_report_store2` for each `int16_t` store to `block[]` (IDCT computation)
- Contains `__asan_report_store1` for each `uint8_t` store to `dst[i]` (frame pixel output)

The instrumentation is correct; the OOB writes simply do not extend past the pool allocation boundary in this build configuration.

## When the Vulnerability IS Exploitable

The overflow CAN cause a real out-of-bounds write when the frame buffer is allocated by an **external custom allocator** that provides exactly `height * linesize` bytes (no 32-row extra alignment). This applies to:

1. Applications that set `avctx->get_buffer2` to a custom callback
2. Decoders running with `AV_CODEC_CAP_DR1` where the caller supplies its own frames
3. Embedded/custom FFmpeg integrations without the standard pool padding

In those cases, with HEIGHT=100 and NSLICES=1, the last 12 rows of writes (rows 100–111) would write 4,608 bytes past the end of the frame buffer — sufficient to cause a crash or corruption.
