--- ANALYSIS ---
Status: VERIFIED_BEHAVIOR

The vulnerable code path IS reached and the buggy case 0x22 IS executed.
Evidence: debug log shows "[dvbsub] Missing display_end_segment, emulating" which
is only printed when all three segments (page/region/object) were fully processed,
confirming that dvbsub_parse_pixel_data_block entered case 0x22 and read 16 bytes
past buf_end.

Why ASAN does not fire:
  - AV_INPUT_BUFFER_PADDING_SIZE = 64 bytes of zeroed memory follows every FFmpeg
    AVPacket allocation (set by memset in new_pes_packet / av_new_packet).
  - The pool allocates max_packet_size + 64 bytes; the OOB read (16 bytes) starts
    within the valid data and extends into this padding area — still within the
    physical allocation boundary.
  - ASAN only poisons memory past the allocation end; since the 16-byte OOB lands
    in the 64-byte padding, no ASAN shadow-memory violation is triggered.

The vulnerability is real and exploitable when libavcodec is called without the
mandatory AV_INPUT_BUFFER_PADDING_SIZE padding (e.g., in custom integrations or
when packets are constructed without ff_alloc_extradata / av_new_packet). In those
contexts this OOB read would access unmapped or foreign-object memory.
