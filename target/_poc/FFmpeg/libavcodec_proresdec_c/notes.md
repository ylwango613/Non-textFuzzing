# VULN 001: decode_slice_thread 2-byte OOB Heap Read

## Summary

- **File**: `FFmpeg/libavcodec/proresdec.c`
- **Function**: `decode_slice_thread()`
- **Line**: 665
- **CWE**: CWE-125 (Out-of-bounds Read)
- **Codec**: Apple ProRes (`apcn`, `apch`, `apcs`, etc.)

## Vulnerable Code

```c
// Line 659-665 in decode_slice_thread():
hdr_size = buf[0] >> 3;
qscale = av_clip(buf[1], 1, 224);
qscale = qscale > 128 ? qscale - 96 << 2: qscale;
y_data_size = AV_RB16(buf + 2);
u_data_size = AV_RB16(buf + 4);
v_data_size = slice->data_size - y_data_size - u_data_size - hdr_size;
if (hdr_size > 7) v_data_size = AV_RB16(buf + 6);  // <-- LINE 665: OOB if data_size==6
```

## Root Cause

The minimum slice data size is enforced as >= 6 bytes (checked in `decode_picture_header()`
at line 397). However, when `buf[0] >= 0x40` (making `hdr_size = buf[0]>>3 >= 8 > 7`),
line 665 reads `AV_RB16(buf + 6)`, accessing bytes `buf[6]` and `buf[7]`. If the slice
`data_size == 6`, those two bytes lie outside the slice's valid data region, constituting
a 2-byte out-of-bounds heap read.

## Trigger Conditions

1. **slice data_size == 6**: Achieved by setting the 16-bit big-endian slice index table
   entry to `0x0006`.
2. **slice buf[0] >= 0x40**: The first byte of the slice data must be >= 64, so that
   `hdr_size = buf[0] >> 3 >= 8 > 7`. We use `0x40` exactly, giving `hdr_size = 8`.

## Expected Behavior

1. `avformat_open_input()` parses the MOV container successfully.
2. `avcodec_send_packet()` dispatches the 44-byte ProRes sample.
3. `decode_frame()` validates "icpf" and calls `decode_frame_header()` -> succeeds.
4. `decode_picture_header()` parses 1 slice with `data_size=6` -> passes the `< 6` check.
5. `decode_slice_thread()` is invoked for slice 0:
   - `hdr_size = 0x40 >> 3 = 8 > 7` -> takes the `if (hdr_size > 7)` branch
   - **OOB read**: `AV_RB16(buf + 6)` reads 2 bytes at `buf+6` and `buf+7`, beyond slice
6. Subsequent validity check (line 669) catches the invalid sizes and returns
   `AVERROR_INVALIDDATA`. ffmpeg prints "invalid plane data size" or similar.

## ASAN Detection Note

FFmpeg allocates packet data with `AV_INPUT_BUFFER_PADDING_SIZE` (64 bytes) of zero
padding appended after the sample data. Because of this padding, the 2 bytes read at
`buf+6` (= `mdat_data + 44`) fall within the allocated heap buffer (in the padding
region), so AddressSanitizer **may not** report a `heap-buffer-overflow`. The OOB read
is real but may only be detectable with Valgrind memcheck (which tracks logical
allocation sizes, not just memory page boundaries) or by inspecting the "invalid plane
data size" error message that proves the corrupted `v_data_size` value was used.
