The vulnerable code path is confirmed present (cfhdencdsp.c:34,46 reads input[4]/input[5] unconditionally). However, the encoder allocates dwt_buf with w8 = width/8 + 64 (a 64-element width padding), so even with width=16 the buffer is large enough that input[4] and input[5] fall within the allocated region at the deepest DWT level. ASAN (address,undefined sanitizer active in build) reported no violation; the run completed cleanly with EXIT=0. The padding likely masks the OOB for small widths; a different allocation path or a build without the +64 guard would be needed to produce an addressable crash.
