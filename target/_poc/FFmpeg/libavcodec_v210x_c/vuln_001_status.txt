--- Why ASAN did not trigger ---

The integer truncation vulnerability in decode_frame() at v210x.c:48 IS present:

  if (avpkt->size < avctx->width * avctx->height * 8 / 3)

For width=2, height=1081 (height%3 == 1):
  Truncated threshold  = floor(2 * 1081 * 8 / 3) = 5765 bytes
  Actual bytes decoder reads = (1080 / 3) * 16 + 8 = 5768 bytes
  Out-of-bounds overread      = 3 bytes

The vulnerability is MASKED by AV_INPUT_BUFFER_PADDING_SIZE = 64 bytes (defined
in libavcodec/defs.h).  FFmpeg allocates ALL AVPacket data buffers with an extra
64 bytes of zero-padded guard space beyond avpkt->size.  The 3-byte OOB read
falls entirely within that padding zone; ASAN redzones are placed only AFTER the
64-byte padding, so the overread never enters poisoned memory.

--- Mathematical proof that OOB < 64 always ---

For width w = 6m+2 (m >= 0) and height h = 3k+1 (k >= 0):

  Bytes actually read by decoder:
    Full 3-row iterations: k groups × (4 uint32 reads × ... for partial rows)
    Last partial (1 row):  2 uint32 reads (breaks at CHECK A, line 74)
    Total: (16k + 8) bytes   [for w=2; scales similarly for other w%6==2 widths]

  Size check threshold (truncated):
    floor(w * (3k+1) * 8 / 3) = floor(16k + 16/3) = 16k + 5   [for w=2]

  OOB = (16k + 8) - (16k + 5) = 3 bytes   ← independent of k (height)

For h%3 == 2: OOB = 2 bytes.
For h%3 == 0: OOB = 0 bytes (no truncation, exact fit).

The maximum possible OOB through this code path is 3 bytes — always less than
the 64-byte padding.  ASAN cannot be triggered via the standard ffmpeg CLI for
this vulnerability.

A custom C harness (prohibited by task constraints) that:

Without bypassing AV_INPUT_BUFFER_PADDING_SIZE, the vulnerability exists in
