# VULN-001: Heap Buffer Overflow in tqi_idct_put

## Vulnerability Summary

- **File**: `libavcodec/eatqi.c`
- **CWE**: CWE-122 (Heap-based Buffer Overflow)
- **Functions**: `tqi_decode_frame()` (lines 136–165), `tqi_idct_put()` (lines 92–110)

## Root Cause

`tqi_decode_frame()` reads `w` and `h` from the packet header (LE uint16 at offsets 0 and 2), calls `ff_set_dimensions(avctx, w, h)`, then calls `ff_get_buffer()` which allocates a frame of exactly `w × h` pixels.

The macroblock loop iterates over `(h+15)/16` rows and `(w+15)/16` columns.  With `w=h=1`, this is exactly **one** macroblock.  `tqi_idct_put()` then calls `ff_ea_idct_put_c()` four times on the luma plane (blocks 0–3), writing **8 rows of 8 pixels each** (a full 16×16 luma macroblock) into the frame buffer.

Because the frame was allocated for only **1 row**, writing rows 1–15 of luma data goes past the end of the heap allocation — a classic heap buffer overflow.

## PoC Construction

### Container Format (EA Multimedia, `.ea`)

The EA demuxer (`libavformat/electronicarts.c`) is detected by `ea_probe()` which requires the first 4 bytes to be one of a set of known block tags.  Each block is:

```
[4-byte tag][4-byte total-size LE][payload]
```

The file contains two blocks:

1. **`SCHl` block (19 bytes)** — passes `ea_probe()` (the `SCHl` tag is in the probe allowlist).  Its payload sets `ea->audio_codec = AV_CODEC_ID_PCM_S16LE` via a minimal audio-header element sequence.  This is needed so `process_ea_header()`'s codec-search loop exits cleanly (it stops when both audio and video codecs are found) without reading a non-existent third block.

2. **`pIQT` block (20 bytes)** — `pIQT` is the EA tag for TQI intra frames (`AV_CODEC_ID_TQI`).  `process_ea_header()` sets `ea->video.codec = AV_CODEC_ID_TQI`.  `ea_read_packet()` subsequently delivers the block's 12-byte payload as a key video packet to `tqi_decode_frame()`.

### TQI Packet (12 bytes)

```
offset  size  value  description
------  ----  -----  -----------
0       2     0x0001 width  = 1  (AV_RL16)
2       2     0x0001 height = 1  (AV_RL16)
4       1     0x10   quant  = 16
5       3     0x00   padding
8       4     ...    MPEG-1 intra bitstream (bswap-encoded, see below)
```

`tqi_decode_frame()` checks `buf_size >= 12` (satisfied), advances past 8 header bytes, then byte-swaps the remainder with `bswap_buf` and passes it to `init_get_bits`.

### Bitstream Encoding

The 4 payload bytes must encode 6 MPEG-1 intra DCT blocks (4 luma + 2 chroma) each with DC coefficient = 0 and no AC terms.

After `bswap32`, the decoder's bit buffer must contain (MSB-first):

| Block | DC VLC             | EOB    | Total |
|-------|--------------------|--------|-------|
| 0–3   | `100` (luma,  3b)  | `10`   | 5 b   |
| 4–5   | `00`  (chroma, 2b) | `10`   | 4 b   |

Concatenated: `10010 10010 10010 10010 0010 0010` = 28 bits, padded to 32 = `0x94 0xA5 0x22 0x20`.

Because `bswap32` reverses byte order within each 32-bit word, the **file bytes** that produce this post-bswap buffer are: `[0x20, 0x22, 0xA5, 0x94]`.

### Overflow Trigger Path

```
ffmpeg -i vuln_001_input.ea -f null -
  → avformat_open_input()
  → ea_probe() passes
  → ea_read_header() / process_ea_header():
       detects TQI video codec from pIQT block
  → avformat_find_stream_info() / ea_read_packet():
       delivers 12-byte packet to eatqi decoder
  → tqi_decode_frame():
       w=1, h=1 → ff_set_dimensions(1,1) → ff_get_buffer (1-row frame)
       tqi_decode_mb() succeeds (valid MPEG-1 bitstream)
       tqi_idct_put():
         ff_ea_idct_put_c(dest_y + 8*linesize, ...) ← OOB WRITE
```

## Why ASAN Does Not Trigger in the Current Build

`libavutil/frame.c` `get_video_buffer()` computes:

```c
padded_height = FFALIGN(frame->height, 32);
av_image_fill_plane_sizes(sizes, format, padded_height, linesizes);
```

For `height=1`, `padded_height = 32`. The Y plane is allocated with 32 rows (not 1),
and the Cb/Cr planes each get 16 rows. A single macroblock writes to luma rows 0–15
and chroma rows 0–7, both of which fit entirely within the padded allocation.

The overflow is mathematically impossible in the current codebase:
- `FFALIGN(h, 32)` is always ≥ `FFALIGN(h, 16)`, the latter being exactly the number
  of luma rows one macroblock column writes.
- The chroma allocation (`FFALIGN(h, 32) / 2`) is always ≥ macroblock chroma writes
  (`(h+15)/16 * 8`).

Multiple variants were tried (h=1, h=17 exact-fit, h=32, large bitstream, no-EOB
bitstream). None triggered ASAN. The vulnerability as described existed in older
FFmpeg versions before this mitigation was applied to `libavutil/frame.c`.
