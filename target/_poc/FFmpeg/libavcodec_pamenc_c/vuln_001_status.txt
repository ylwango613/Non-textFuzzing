VULN_001_STATUS: FAILED

Vulnerability: libavcodec/pamenc.c :: pam_encode_frame()
Type:          CWE-190 (Integer Overflow) -> CWE-122 (Heap-Based Buffer Overflow)
Trigger file:  vuln_001_input.tiff (MONOBLACK TIFF, w=16384, h=262144)
Binary:        /data/ylwang/non-textfuzz/target/FFmpeg/build_test/ffmpeg (ASAN+UBSAN)

VULNERABILITY CONFIRMED IN CODE: YES
  pamenc.c line 102: `n*h + header_size` computed as signed int32 with no overflow guard.
  For RGBA64BE (n = 8*w = 131072, h = 32769): n*h = 4,295,098,368 wraps to +131072 -> heap overflow.
  For MONOBLACK (n = w = 16384, h = 262144): n*h = 4,294,967,296 wraps to 0 -> allocation ~76 bytes.

SANITIZER TRIGGERED: NO
  UBSAN signed-integer-overflow: not reached
  ASAN heap-buffer-overflow: not reached

REASON FOR FAILURE:
  av_image_check_size2() (libavutil/imgutils.c) with AV_PIX_FMT_NONE (used by ff_set_dimensions)
  computes worst-case stride = 8*w regardless of actual pixel format.

  For w=16384: stride = 8*16384 = 131072, then stride + 1024 = 132096.
  The check: 132096 * (h + 128) >= INT_MAX => blocks h >= 16253 for this width.

  Any dimensions large enough to trigger n*h overflow (n*h > INT_MAX) satisfy:
    8*w*h >= n*h > INT_MAX  (since n <= 8*w for all PAM-supported formats)
  Therefore (8*w+1024)*(h+128) > 8*w*h > INT_MAX -> check always REJECTS.

  Mathematical proof of impossibility via ffmpeg binary:
    TRIGGER condition:  n*h > INT_MAX     => 8*w*h >= n*h > 2^31
    SIZE-CHECK pass:    (8*w+1024)*(h+128) < INT_MAX
    (8*w+1024)*(h+128) > 8*w*h > INT_MAX  =>  size check FAILS whenever trigger is met.
    The two conditions are mutually exclusive. No valid media file can bypass this.

APPROACHES ATTEMPTED:

EXPLOITABILITY:
  The vulnerability IS exploitable but ONLY via direct libavcodec API usage where an application
  creates an AVFrame with oversized dimensions (bypassing standard size checks) and passes it
  directly to the PAM encoder. This cannot be triggered by a crafted media file alone.
