# VULN 001: Heap OOB Read in ff_combine_frame via Negative Overread Index

## Vulnerability Summary

**File**: `libavcodec/parser.c`, lines 223-224, 255-256, 283-285  
**Type**: Heap Out-of-Bounds Read  
**Severity**: Medium-High (information disclosure, potential crash)

## Root Cause

`ff_combine_frame()` in `libavcodec/parser.c` uses the `next` value returned by
codec-specific parsers (e.g., `hevc_find_frame_end()`) to index into `pc->buffer`.
When the HEVC parser finds a new frame boundary at position `i=0` while
`pc->index < 6`, it returns `next = i - 6 = -6`.

The function then computes:
- `pc->last_index + next` = `pc->index + (-6)` = negative value
- `pc->overread_index` = negative value

These negative indices are used to access `pc->buffer[negative_index]`, which
reads heap memory before the start of the allocated buffer — a classic heap OOB read.

## Trigger Conditions

1. First HEVC packet: very small (3-5 bytes), so `pc->index < 6` after buffering.
2. Second HEVC packet: starts immediately with a new NAL unit start code (`00 00 01`)
   followed by a frame-boundary NAL type (VPS=32, SPS=33, PPS=34).
3. The HEVC parser detects the new frame at `i=0` in the second packet,
   returning `next = 0 - 6 = -6`.

## PoC Approach

A minimal MKV (Matroska) container is crafted with:
- **Track**: HEVC video (`V_MPEGH/ISO/HEVC`)
- **Block 1** (timecode=0, 3 bytes): `00 00 01` — partial/incomplete start code,
  sets `pc->index = 3` (< 6)
- **Block 2** (timecode=33, 29 bytes): full VPS NAL unit starting at byte 0,
  triggering `hevc_find_frame_end()` to return `next = -6`

The crafted file uses valid EBML/Matroska structure to be accepted by the
demuxer, while the HEVC payload is designed to exercise the boundary condition
in the parser's frame-combining logic.

## Expected Behavior Without Fix

ASAN should report a heap-buffer-underflow or heap-buffer-overflow read at
`parser.c:284` (or nearby) when `pc->buffer` is indexed with a negative offset.
