# VULN 003 - APE Tag Length Overflow -> NULL Pointer Dereference

## Vulnerability

- **CWE**: CWE-476 (NULL Pointer Dereference)
- **Function**: `ReadMP3APETag()` in `apetag.c`, lines 170-172
- **Binary**: mp3gain

## PoC Approach

A minimal file is crafted containing:
1. One valid MPEG1 Layer3 MP3 frame (to satisfy basic MP3 parsing)
2. An APEv2 footer appended at the end of the file

The APE footer's `Length` field (bytes 12-15 of the 32-byte footer) is set to
`0xFFFFFFFF` (4,294,967,295 = ~4GB). This value is read as `TagLen` by
`ReadMP3APETag()`.

## Vulnerable Code Path

```
mp3gain main()
  -> ReadMP3GainAPETag()
  -> ReadMP3APETag()
      TagLen = read LE32 from footer offset 12   // 0xFFFFFFFF
      if (TagLen >= sizeof(T)) {                  // sizeof(T) << 4GB, passes
          buff = (char *)malloc(TagLen);           // malloc(4GB) returns NULL
          fread(buff, 1, TagLen - sizeof(T), fp); // fread(NULL, ...) -> CRASH
      }
```

## Trigger Path

`mp3gain <file>` -> `ReadMP3GainAPETag()` -> `ReadMP3APETag()` detects `"APETAGEX"`
magic near end of file, reads the footer's Length = 0xFFFFFFFF, calls
`malloc(0xFFFFFFFF)` without NULL check, then calls `fread()` with the NULL pointer.

## Expected Phenomena

- On memory-constrained systems: `malloc(4GB)` returns NULL, `fread(NULL, ...)` triggers
  a segmentation fault (SIGSEGV).
- With ASAN: AddressSanitizer may report a null-dereference or heap allocation failure
  error.
- Without memory pressure: on 64-bit systems with plenty of virtual memory, `malloc(4GB)`
  may actually succeed, allocating 4GB of virtual memory, in which case the crash may
  not trigger (the fread would simply try to read 4GB from a short file and return early).

## Limitations

- **UNVERIFIED on 64-bit systems with sufficient virtual memory**: Modern 64-bit Linux
  kernels with sufficient overcommit settings may allow a 4GB malloc to succeed, masking
  the vulnerability.
- The crash is more reliably triggered on 32-bit systems (where 4GB exceeds address space)
  or systems with ASAN's internal allocation limits.
- If malloc succeeds, the program will attempt a very large fread(), which will return
  a short count (file is only ~449 bytes), but `buff` won't be NULL, so no crash occurs.
