# VULN 001: APE Tag MP3GAIN_UNDO Heap Buffer Over-Read

## PoC Approach

A crafted binary file is generated by `vuln_001_gen.py` using Python's `struct` module.
The file layout is:

```
[417-byte minimal MPEG1 Layer3 frame]
[21-byte APE item: vsize=0, key="MP3GAIN_UNDO"]
[32-byte APEv2 footer]
```

The APEv2 footer magic `APETAGEX` at the end causes mp3gain to detect and parse the tag.
The single APE item has `value_size = 0`, which is the root trigger.

## Trigger Path

```
mp3gain main()
  → ReadMP3GainAPETag()     [apetag.c:356]
    → ReadMP3APETag()       [apetag.c:142]
      → fseek to file_size - 32, reads footer ("APETAGEX" found)
      → reads TagLen=53 bytes from end, allocates buff
      → item loop: vsize=0, flags=0, key="MP3GAIN_UNDO"
      → bounds check passes (isize=12 < remaining=13, 12+1+0 == 13, not '>') [line 202]
      → value = malloc(vsize+1) = malloc(1)   [line 207]
      → _stricmp(name, "MP3GAIN_UNDO") matches [line 226]
      → vp = value                             [line 229]
      → memcpy(tmpString, vp, 4)  ← OOB READ  [line 230]  heap-buffer-overflow
```

## Root Cause

`apetag.c` only checks the upper bound on `vsize` (`vsize > MAX_FIELD_SIZE`) but not a
lower bound. When `vsize = 0`, `malloc(1)` allocates one byte, but the MP3GAIN_UNDO
branch unconditionally reads 4 bytes via `memcpy(tmpString, vp, 4)`, reading 3 bytes
past the end of the heap allocation.

## Expected Phenomena

- ASAN reports `heap-buffer-overflow` (READ of size 4) in `ReadMP3APETag`
- Stack trace shows: `memcpy` → `ReadMP3APETag` → `ReadMP3GainAPETag` → `main`
- Crash or sanitizer abort depending on ASAN configuration
- CWE-125: Out-of-bounds Read
